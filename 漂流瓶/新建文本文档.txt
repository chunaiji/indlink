Score =
标签匹配 * 0.5

+ 兴趣相似度 * 0.2
+ 随机探索 * 0.1

热度机制
热度 = 回复数 × 3 + 点赞 × 1 + 停留时间

一、后端语言选型（结论先说）
🥇推荐：Go（首选）
为什么适合你这个产品：
协程天然高并发（几万连接没问题）
内存占用低（2C4G非常关键）
写 API + WebSocket 都很稳
部署简单，一个二进制文件

👉 非常适合：

feed刷流
聊天系统
推荐接口
🥈备选：Node.js（也可以）

适合：

快速开发 MVP
开发效率高

但问题：

CPU密集（推荐算法）容易卡
GC抖动
长期高并发不如 Go 稳
❌不建议：
Java（2C4G太重）
Python（除非只做AI服务）

五、高并发核心设计（重点）
1️⃣ Feed 必须走 Redis
❌错误做法：

每次请求：

→ 查 MySQL → 计算 → 返回

👉 直接爆

✔正确做法：
用户请求 feed
→ Redis 直接返回缓存列表
Redis结构：
user_feed:{user_id} = [bottle_id1, bottle_id2...]
2️⃣ 写操作异步化（非常重要）

例如：

点赞
回复
浏览记录
❌同步写 MySQL：

慢 + 卡

✔正确：
用户操作 → Redis → MQ → MySQL

没有 MQ 也可以先：

👉 Redis List 先堆着，定时刷库

3️⃣ 聊天必须用 WebSocket
架构：
Client
  ↓
Go WebSocket Server
  ↓
Redis Pub/Sub（可选）
关键优化：
在线用户存在 Redis
消息只写一次 DB
最近消息缓存 Redis
4️⃣ 推荐系统不要实时算
❌错误：

用户刷一次算一次

✔正确：

定时生成：

每5分钟：
→ 给用户生成 feed list
→ 存 Redis
六、2C4G服务器极限优化方案
CPU优化
Go协程池
避免 JSON 大对象
减少 ORM（用 SQL）
内存优化
Redis 控制 TTL
feed 列表限制 50~100条
不缓存大对象
带宽优化
图片走 OSS/CDN
feed 只传 ID + 少量内容
