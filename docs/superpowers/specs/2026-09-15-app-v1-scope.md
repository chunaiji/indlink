## 二、逐模块现状与缺口

### 1. Auth & User — 改造 + 新增

现有 `user.resolveLogin` 只有 `wx` / `alipay` 两个分支，走 code2session。`model.User` 已有 `Gender` / `Age` / `City`。

| 能力 | 现状 | 工作 |
|---|---|---|
| Mobile OTP | 无 | 🆕 短信服务商 + 验证码存 Redis + 频控。**印度发短信须先在 TRAI DLT 平台注册实体与模板**，这是开户前置，不是代码工作 |
| Google 登录 | 无 | 🆕 ID Token 校验 |
| Apple 登录 | 无 | 🆕 **一旦有 Google 登录，App Store 4.8 强制要求配套 Apple 登录** |
| profile | 部分 | ✅ 复用 |
| language / interests / location | **无字段** | 🔨 `User` 加 `Language` / `Interests` / `Lat` / `Lng`（AutoMigrate 自动加列） |

租户识别沿用既有 spec §5.2 方案：`app_credentials` 增加 `platform = "app"` 一行。

### 2. Bottle ⭐ — 复用

`Bottle` 表已含 `ExpireAt` + `Status(active/expired/deleted)`，过期机制完备；`BottleReply` + `ReplyUnlock` 覆盖回信与解锁；限次走 `quota`。捞瓶 Redis feed 与打分权重后台可调。**后端零改动。**

### 3. Match ⭐ — 改造（注意语义不同）

现有 `match` 模块实际是**「瓶子推荐打分 + MatchLog 行为记录」**，不是「人对人发现」。`MatchLog` 记录的是 viewer 对 bottle 的 view/like/reply/skip。

V1 要的 "user discovery, matching based on language/interests/location" 是**新语义**：按语言/兴趣/地理找人。现有打分逻辑可借鉴，但需要新的候选集来源（用户池而非瓶子池）与新的相似度维度。依赖模块 1 先补齐 language/interests/location 字段。

### 4. Chat ⭐ — 复用 + 补

| 能力 | 现状 |
|---|---|
| 1-to-1 文字 | ✅ `chat` + WebSocket |
| 图片 | ✅ `Message.Type` 已支持 `image` |
| 已读状态 | ✅ `Message.ReadStatus` 字段已有 |
| 拉黑 | ✅ `Block` 表已有 |
| **在线状态** | ❌ 无。`User.LastActiveAt` 可做「最近活跃」降级方案 |

已知架构缺口：chat Hub 是**单实例内存态**，多实例部署会丢消息。V1 若只单机部署可暂不处理，需在部署方案中明确。

### 5. Relation — 复用

`model.Relation` 已含 `Type(like/viewed/friend)` / `StrengthScore(0~100)` / `Stage` / `InteractionCount` / `LastInteractionAt`，与 V1 描述的 "likes, connections, interaction/relationship strength" **完全对应**。

### 6. Moment — 复用

`Moment`（含 `Images` JSON 数组 ≤9 张）/ `MomentLike` / `MomentComment`（单层可回复、支持礼物评论）齐备。

### 7. Media — 改造（必做）

现状 `upload` **落本地磁盘**，通过 `/static` 前缀裸服务，无压缩、无缩略图、无 CDN。代码注释本身已标注「生产切对象存储」。

对印度用户，图片走中国服务器的本地磁盘是**体验硬伤**（首屏图片可能数秒）。需要：对象存储 + 海外 CDN + 服务端压缩缩略图。V1 还新增了 **video** 上传，编码/转码/时长限制均为全新工作。

### 8. Notification & Push — 复用 + 新增

站内通知 `notify` 复用。但 `push` 模块是**微信订阅消息专用**（模板 ID、`PushSubscription.OpenID`、access_token 同源机制），在 App 端**完全不可用**。FCM + APNs 是从零开始：设备 token 表、证书/密钥管理、多端去重、定时任务改造（`push/scheduler.go`）。

### 9. Moderation & Safety ⭐ — 复用 + 替换

| 能力 | 现状 |
|---|---|
| 举报 | ✅ `Report` 表 + 后台处理 |
| 拉黑 | ✅ `Block` 表 |
| 敏感词 | ✅ 本地词库 + 防引流（`moderation`） |
| **图片审核** | ❌ 现为微信 `mediaCheckAsync`，**App 端完全失效**，需换第三方（OpenAI Moderation / AWS Rekognition / 本地模型） |
| spam 控制 | ⚠️ 部分（频控分散在各业务） |

### 10 / 12 / 13. Wallet、Items & Gifts、Quota — 复用

金币体系完整：`Wallet` + `WalletTxn`（credit/debit + scene + `BalanceAfter` 可对账）、`Item` / `ItemOrder` + 送礼三处统一链路、`quota` 免费次数 + 次数包。**基本零改动**，只需把现有的 5 个扣费点与充值档位在 App 端接起来。

### 11. Payment 💰 — 新增 driver（有重大合规前提，见 §三 C2）

`pay` 已有 `Driver` 接口抽象（`Prepay` / `VerifyCallback` / `SuccessResponse`），微信实现完整、支付宝是骨架。新增印度渠道**只需实现一份 Driver**，订单/回调幂等/入账链路全部复用——这部分工程量小。

真正的成本在合规，不在代码。

### 14. Rewards & Ads 💰 — 复用 + 替换

签到 `checkin`（唯一索引保证一人一天一次）、分享 `share` 复用。但 `ad` 模块是**微信流量主**，App 端需换 AdMob，16 个广告位配置体系需重做。

> 与用户先前「流量主等可以都不要」的表述冲突，见 §三 C5。

### 15. Fraud Protection — 全新

现有只有零散频控，无统一反作弊。V1 要覆盖支付欺诈、金币异常、拉新奖励薅羊毛。印度市场的薅羊毛产业化程度高，这块不能省。

### 16. Admin — 复用 + 扩展

22 个视图、166 项配置白名单齐备。新增模块（OTP 日志、印度支付订单、FCM 推送、反作弊规则）需按硬约束登记 `internal/admin/meta.go` 白名单。

### 17. Analytics — 改造 + 新增

`admin/overview.go` 有按东八区口径的 KPI 聚合，但**没有事件埋点体系**。V1 要的 retention events 需要新的事件表/上报接口，或直接接第三方（Firebase Analytics / Amplitude）。

> 注意：若接第三方，现有 KPI 的**东八区时间口径**与第三方默认 UTC/本地时区会对不上，需统一。

## 三、与既有 spec 的冲突登记（必须决策）

`2026-09-14-flutter-app-overseas-design.md` §二 的已确认决策，有 5 项被这份清单推翻。**在解决之前，两份文档处于自相矛盾状态。**

| ID | 冲突点 | 旧决策 | V1 清单 | 影响 |
|---|---|---|---|---|
| **C1** | 登录方式 | 邮箱 + 密码，Google 放迭代 1 | Mobile OTP + Google/Apple | 邮箱方案是否作废？OTP 需短信服务商 + **印度 DLT 注册**；Google 进 V1 → **Apple 登录强制** |
| **C2** | 变现 | 「第一版不做，无充值、无广告、无 IAP」 | 5 个 💰 模块全进 V1 | 见下方 IAP 说明 |
| **C3** | 目标市场 | 「海外为主」（未指定国家） | Indian payment → **印度** | 触发一批印度特定合规；R1 风险等级上升 |
| **C4** | 范围 | MVP 五屏 | 17 模块 | 旧 spec §3.2「明确不做」清单几乎全部作废 |
| **C5** | 广告 | 用户原话「流量主等可以都不要」 | Rewards & Ads 在 V1 | 是否确实要做激励视频广告？ |

### C2 展开：iOS 上印度支付渠道用不了

这是整份清单里代价最大的一条，必须先定：

- **App Store 3.1.1**：App 内消费的数字商品（金币、礼物、道具、次数包）**必须走 IAP**，抽成 30%（小企业计划 15%）。Razorpay / UPI / 任何第三方渠道在 iOS 上**会被拒审**。
- **Google Play Billing** 同理。印度因 CCI 反垄断裁决允许替代计费，但需单独备案且仍收服务费——**具体政策请在启动前向 Google 确认现行条款**。
- 结论：**"Indian payment integration" 实际只能覆盖 Android 侧**。iOS 必须另做一套 IAP + 票据校验（服务端验 receipt、防重放、掉单补偿）。
- 连锁后果：同一份金币在两端**价格与到账链路分叉**，`PayOrder.Platform` 需扩展，运营配置的充值档位要按平台拆分。

> 引导用户去站外网页充值同样违规（3.1.3 / 4.2）。这条没有绕过路径。

沿用旧 spec 的 R1–R6，新增：

| ID | 风险 | 影响 | 缓解 |
|---|---|---|---|
| **R7** | 后端在腾讯云国内节点服务印度用户 | 延迟高于海外泛指场景；且印度对中国背景 App 有持续监管动作，中国 IP 托管的匿名社交 App 风险显著 | **R1 从「MVP 可接受」升级为 V1 前置项**。建议评估印度本地或新加坡节点 |

| **R9** | 印度 DPDP Act 2023 数据保护合规 | 个人数据跨境传输、用户同意、删除权 | 提审前完成法务评估 |

| **R11** | 范围从 5 屏扩到 17 模块 | 不再是可快速验证的 MVP，一次性交付周期长、风险集中 | 建议对 17 模块做**上线批次分层**（见 §五） |

## 五、建议：V1 内部分层

17 个模块一次性交付周期过长。按「上架资格 → 体验闭环 → 变现」分三批，每批可独立提审：

| 批次 | 模块 | 目标 |
|---|---|---|
| **V1.0** | 1 Auth · 2 Bottle · 4 Chat · 7 Media · 9 Moderation · 16 Admin | 拿到上架资格（UGC 合规四件套齐备） |
| **V1.1** | 3 Match · 5 Relation · 6 Moment · 8 Push · 17 Analytics | 体验闭环 + 留存 + 数据可观测 |
| **V1.2** | 10 Wallet · 11 Payment · 12 Items · 13 Quota · 14 Rewards&Ads · 15 Fraud | 变现（等 C2 / R10 结论落地后启动） |

理由：变现批次的**外部依赖最重**（支付牌照、IAP 配置、DLT 注册），把它放在最后可以避免非代码因素阻塞整个 V1 上线。模块 10/12/13 后端几乎零改动，延后成本极低。
