Start here: they are not interchangeable

The most common and most expensive mistake is assuming one Google credential covers everything. These three come from different consoles, look nothing alike, and cannot substitute for one another.

FeatureCredential typeCreated inCarries a secret?
Google Sign-In OAuth 2.0 client Google Cloud Console → Credentials The web client has one, but this project never uses it
Google Maps API key Google Cloud Console → Credentials No
Play Billing Service account key Google Play Console → API access Yes — a JSON private key

Two consequences worth stating plainly. An OAuth client JSON cannot be used for Maps, and an API key cannot be used for Sign-In. And the product behind in-app coin purchases is Google Play Billing, not Google Pay — Google Pay is for physical goods and services, while coins are digital goods consumed inside the app, which Google requires to go through Play Billing. Shipping Google Pay for this would fail review.

Never commit No client_secret, service account JSON, or API key value belongs in the repository. android/local.properties and ios/Flutter/Maps.xcconfig are already gitignored — key values live there, never inline in AndroidManifest.xml or Info.plist. Guard the Maps keys hardest: a leaked one is billed to your account until somebody notices.

Google Sign-In

Configurable · code gaps remain

What the backend actually checks

The server never calls Google's token endpoint. It fetches Google's public keys from the JWKS endpoint, verifies the ID token's RS256 signature, and checks iss, aud and exp.

So the client_secret is not used anywhere in this project. A client secret is only needed for the authorization-code exchange, which we never perform. If somebody hands you a client_secret_*.json, you need exactly one field out of it — client_id — and the rest can be discarded.

Create three OAuth clients

All three live in the same Google Cloud project, under APIs & Services → Credentials → Create credentials → OAuth client ID.

Application typeWhat you must supplyWhat comes back
Web application Nothing Client ID — this is the one the backend verifies against
Android Package name com.ambertu.bottles + SHA-1 fingerprint Client ID. Nothing to download — the pairing itself is what matters
iOS Bundle ID com.ambertu.bottles Client ID + a reversed-client-ID URL scheme

The Android and iOS clients produce no file to copy into the project. Google identifies the app by package name plus signing fingerprint on Android, and by bundle ID on iOS. Creating them is what makes sign-in work; there is nothing further to paste.

Not this one A credential of type Desktop app — its JSON has an "installed" key — is not usable here. It exists for CLI and desktop programs. If you have one, set it aside.

Getting the Android SHA-1 fingerprints

You need two, and both must be registered. Register only one and sign-in works on a developer machine while silently failing on the installed release build.

# Debug keystore — identical on any machine using the default Android debug key
keytool -list -v \
  -keystore ~/.android/debug.keystore \
  -alias androiddebugkey -storepass android -keypass android

# Release keystore — substitute your own path and alias
keytool -list -v -keystore /path/to/release.keystore -alias <your-alias>

Take the SHA1: line from each. If the app ships through Google Play with Play App Signing enabled, also register the SHA-1 shown in Play Console under Release → Setup → App signing — Google re-signs the uploaded artifact, and that is the fingerprint end users actually run.

Two code gaps that block sign-in regardless

Configuring everything above is necessary but not sufficient. These are recorded here so nobody spends a day re-checking console settings that were already correct.

  • Android never receives an ID token. oauth.dart calls GoogleSignIn().signIn() with no serverClientId, and the project has no google-services.json to supply default_web_client_id. With neither present, auth.idToken comes back null and the app throws “Google did not return an ID token”. The fix is to pass the web client ID as serverClientId — no Firebase project and no Gradle plugin needed.
  • The backend accepts only one audience. It validates aud against the single app_google_client_id. In practice Android yields aud = the web client ID once serverClientId is set, while iOS yields aud = the iOS client ID. Google's own guidance is to accept any of your client IDs, so as written one platform will always be rejected. The fix is to allow a list.

Google Maps

Ready — code is waiting on keys

Enable these APIs

Under APIs & Services → Library: Maps SDK for Android, Maps SDK for iOS, and Geocoding API.

Create three separate keys

Under Credentials → Create credentials → API key. Use three distinct keys, one per surface. Do not reuse a single key — each carries a different restriction, and a key restricted for one surface will not work on the others.

KeyApplication restrictionAPI restriction
Android Maps Android apps → package com.ambertu.bottles + the same SHA-1 fingerprints as above Maps SDK for Android
iOS Maps iOS apps → bundle ID com.ambertu.bottles Maps SDK for iOS
Server geocoding IP addresses → 175.178.182.166 Geocoding API

The server key is the one that would hurt most if it leaked, because an IP restriction is the only thing between it and open internet use. Restrict it before pasting it anywhere.

Where the values go

KeyDestination
Android MapsAdd MAPS_API_KEY=<key> to app/bottles/android/local.properties
iOS MapsCopy ios/Flutter/Maps.xcconfig.example to Maps.xcconfig, replace the placeholder
Server geocodingAdmin → System settings → App location → app_google_map_key

Both local files are gitignored. The Android key is injected at build time via manifestPlaceholders, keeping AndroidManifest.xml free of secrets; the iOS key reaches Info.plist through the xcconfig and is read in AppDelegate.swift.

Easy to miss Set app_maps_provider to google under Admin → System settings → App location. Left empty, the server keeps using Tencent Location Service — the existing mini-program behaviour. You can configure the geocoding key perfectly and still see zero Google traffic if this switch is not flipped.

What happens without a key

Nothing hard-fails, so it is safe to configure one surface at a time. Android still builds; the map renders as a blank grey area and logs a key error while the rest of the app works normally. The server falls back to returning raw latitude and longitude with an empty place name instead of erroring, so a user can still drop a pin — it just has no readable label.

Google Play Billing

Blocked — nothing to configure yet

There is nowhere to put a Play credential right now. Obtaining one today means holding a private key with no home.

  • Backend: the database tables and the price-selection helper exist. The service-account authentication layer, the purchase-verification endpoint, refund polling and admin price management do not.
  • Config: the four sysconfig keys this feature needs have not been created, so the admin console shows no Play fields at all.
  • Client: pubspec.yaml has no in_app_purchase dependency; no Flutter work has started.

Roughly 9 of 31 planned steps are complete.

What it will require, once the work is scheduled

A service account key, obtained through Google Play Console rather than Google Cloud Console:

  1. Play Console → Setup → API access
  2. Link the Google Cloud project — the same one used for Sign-In and Maps
  3. Create a service account, then grant it View financial data and Manage orders and subscriptions
  4. Back in Google Cloud Console, create and download a JSON key for that service account

That JSON is a private key. It belongs in the admin console's encrypted credential storage — never in the repository, and never in a chat message.

Separately, every coin package must exist as a managed product in Play Console, with the product ID matching what the backend stores and prices aligned by hand between the two consoles. The server rejects any purchase whose paid amount does not match.

Suggested order

  1. Create the web, Android and iOS OAuth clients, then set app_google_client_id and app_apple_bundle_id.
  2. Enable the three Maps APIs, create the three restricted keys, then set app_google_map_key and app_maps_provider=google.
  3. Get the two code gaps fixed, then verify sign-in on real Android and iOS hardware.
  4. Leave Play Billing until the backend and client work is scheduled.

Steps 1 and 2 are independent and can happen in either order. Step 3 needs real hardware — an emulator without Google Play services cannot complete Google Sign-In.
